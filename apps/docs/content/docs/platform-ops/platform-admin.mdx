The platform admin console provides operators with a unified view across all workspaces. Monitor resource usage, manage workspace lifecycles, detect noisy neighbors, and enforce plan changes — all from a single dashboard.

<Callout title="Prerequisites">
- Managed auth enabled
- Internal database configured (`DATABASE_URL`)
- `platform_admin` user role (assigned via `ATLAS_ADMIN_EMAIL` at first signup or directly in the database)
</Callout>

## Platform Admin Role

The `platform_admin` role is a user-level role distinct from workspace admin. It is the only value stored in Better Auth's admin plugin `user.role` field; tenant admin-ness (`member` / `admin` / `owner`) lives in `member.role` per workspace (#2890).

| Role | Scope | Purpose |
|------|-------|---------|
| `member` | Workspace | Query data, view conversations |
| `admin` | Workspace | Manage connections, users, settings |
| `owner` | Workspace | Full workspace control, delete org |
| `platform_admin` | Platform | Cross-tenant management, all workspaces |

Platform admins can also access workspace-level admin routes (they inherit admin capabilities).

### Assigning the Role

The first user to sign up (when `ATLAS_ADMIN_EMAIL` matches or no admin exists) is automatically assigned `platform_admin`. To promote an existing user:

```sql
UPDATE "user" SET role = 'platform_admin' WHERE email = 'operator@example.com';
```

## Dashboard

Navigate to **Admin > Platform Admin** in the sidebar. The dashboard tab shows aggregate statistics:

- **Workspaces** — total count with active/suspended breakdown
- **Active Users** — total registered users across all workspaces
- **Queries (24h)** — platform-wide query volume
- **MRR** — monthly recurring revenue estimate based on plan tiers

A bar chart shows the top 10 workspaces by query volume.

## Workspace Management

The workspaces tab lists all organizations with sortable columns and filters for status and plan tier.

### Actions

| Action | Endpoint | Description |
|--------|----------|-------------|
| View | `GET /api/v1/platform/workspaces/:id` | Resource breakdown, user list |
| Suspend | `POST /api/v1/platform/workspaces/:id/suspend` | Block all access |
| Unsuspend | `POST /api/v1/platform/workspaces/:id/unsuspend` | Restore access |
| Delete | `DELETE /api/v1/platform/workspaces/:id` | Soft-delete + cascade cleanup |
| Purge | `POST /api/v1/platform/workspaces/:id/purge` | GDPR hard delete (permanent) |
| Change plan | `PATCH /api/v1/platform/workspaces/:id/plan` | Update plan tier |

All actions require confirmation dialogs in the UI. Delete cascades to conversations, semantic entities, learned patterns, suggestions, and scheduled tasks.

### GDPR Workspace Purge

<Callout type="warn">
Purging a workspace is **irreversible**. All data is permanently removed in a single transaction — there is no undo, no backup recovery, and no way to restore the workspace after purging.
</Callout>

The purge action permanently removes **all** data for a workspace to satisfy GDPR right-to-erasure (Article 17) requests. It deletes every row across all tables scoped to the workspace, including:

- Conversations, messages, agent run transcripts, and audit logs
- **Company Atlas / brain data** — extracted claims (`brain_facts`), the provenance and conflict graph, raw source episodes, the curated identity vocabulary, and audience membership
- **Knowledge Base** — every ingested document, the link graph, sync state, and the encrypted sync connector credentials
- Connections, settings, and plugin configurations
- Semantic entities, entity version history, profiling state, learned patterns, and query suggestions
- Dashboards, cards, per-user drafts, and their cached result snapshots
- Scheduled tasks and task run history
- Integration installations (Slack, Discord, GitHub, Linear, email) and every encrypted credential store
- Proactive chat configuration, pause state, metering, and human review verdicts
- Usage events, token accounting, overage meter reports, SLA metrics, and abuse events
- Custom domains, sandbox credentials, and region migrations
- SSO providers, IP allowlists, custom roles, approval workflows, and the MCP action policy
- Cross-workspace agent grants, scopes, and rate limits
- Workspace branding, onboarding emails, and PII classifications
- Members, invitations, and the organization record itself
- **Orphaned users** — users with no remaining workspace memberships are also deleted (sessions, accounts, and user record)

All operations run in a single database transaction — either everything is purged or nothing changes.

#### Two deliberate exceptions

Not every workspace-scoped row is deleted, and the two exceptions are chosen rather than overlooked. Both are enforced by a per-table registry (`lib/db/purge-scope.ts`) whose tripwire fails CI when a new workspace-scoped table appears without a decision.

- **The admin action log is anonymized, not deleted.** It records what operators *did* to this workspace — suspensions, plan changes, MFA resets — and an erasure should not be able to destroy its own accountability trail on the way out. The purge NULLs `actor_id`, `actor_email`, `ip_address` and `metadata`, and replaces `target_id` with a sentinel. `action_type`, `target_type`, `timestamp` and `org_id` survive, so *what happened* stays auditable and *who it happened to* does not. `metadata` is cleared wholesale rather than key-by-key, because it is free-form and written from many call sites — some of which store a member's email address.
- **Two Stripe tables are retained.** `stripe_teardown_pending` rows *are* the retry that still has to cancel a live subscription — deleting them would strand a subscription invoicing a deleted workspace. `stripe_purged_subscriptions` is the tombstone the purge writes so that cancellation webhooks arriving after the transaction commits cannot regrow ledger rows. Neither holds customer personal data.

A third case is worth naming because it looks like an omission: the one-trial-per-user grant (`user_trial_grants`) deliberately outlives the workspace. It is keyed on the user, and deleting it would let a purged workspace's owner claim a fresh trial on demand. It is removed when the user account itself is deleted.

#### Residue from purges performed before this coverage existed

Purges run before the brain and Knowledge Base tables entered the purge path left their rows behind. Those rows are **precisely identifiable**, because `hardDeleteWorkspace` is the only code path that deletes an `organization` row: a `workspace_id` present in one of these tables with no matching organization is residue from an earlier purge.

The decision: **a sweep is required where the detection query returns anything, and it must be run per region** — there are three independent region databases, and a workspace purged in one leaves nothing in the others. Run the detection first; do not run a blind delete.

```sql
-- Per region. Any row returned is data a completed GDPR purge should have removed.
SELECT 'brain_facts' AS table_name, b.workspace_id, count(*) AS rows
  FROM brain_facts b
 WHERE NOT EXISTS (SELECT 1 FROM organization o WHERE o.id = b.workspace_id)
 GROUP BY b.workspace_id
UNION ALL
SELECT 'brain_episodes', b.workspace_id, count(*)
  FROM brain_episodes b
 WHERE NOT EXISTS (SELECT 1 FROM organization o WHERE o.id = b.workspace_id)
 GROUP BY b.workspace_id
UNION ALL
SELECT 'knowledge_documents', k.workspace_id, count(*)
  FROM knowledge_documents k
 WHERE NOT EXISTS (SELECT 1 FROM organization o WHERE o.id = k.workspace_id)
 GROUP BY k.workspace_id
UNION ALL
SELECT 'knowledge_sync_credentials', k.workspace_id, count(*)
  FROM knowledge_sync_credentials k
 WHERE NOT EXISTS (SELECT 1 FROM organization o WHERE o.id = k.workspace_id)
 GROUP BY k.workspace_id;
```

<Callout type="warn">
Two things to hold before running a deletion. First, a region **import** cannot produce a false positive here — it writes into an already-active organization, so it never leaves rows without one; the orphan signal really does mean "the organization row is gone". Second, that makes the query's output a deletion list against real customer data with no undo, so run it through the operator binary's double-gating (`ATLAS_*_OK=1` plus `--confirm`) and take a `pg_dump` first, exactly as with `ops wipe`. Never hand-run the delete against a region database.
</Callout>

#### Prerequisites

The workspace **must be soft-deleted first** using the Delete action (`DELETE /api/v1/platform/workspaces/:id`). Attempting to purge an active or suspended workspace returns a `409 Conflict` error:

```
Workspace must be soft-deleted before purging. Delete the workspace first, then purge.
```

#### Confirmation

In the platform admin UI, the purge button appears only on workspaces with `deleted` status. Clicking it opens a confirmation dialog that requires you to **type the workspace name** to proceed. This prevents accidental purges.

#### API Reference

```
POST /api/v1/platform/workspaces/:id/purge
```

**Auth:** Requires `platform_admin` role.

**Responses:**

| Status | Description |
|--------|-------------|
| `200` | Workspace purged successfully |
| `401` | Authentication required |
| `403` | Platform admin role required |
| `404` | Workspace not found or internal database not configured |
| `409` | Workspace must be soft-deleted first |
| `500` | Internal server error (includes `requestId` for log correlation) |

**Success response:**

```json
{
  "message": "Workspace permanently purged. All workspace data has been irreversibly deleted; the admin action log is retained with its identifiers scrubbed, and pending Stripe teardown records are kept until they settle. See `purged` for per-table counts.",
  "workspaceId": "org_abc123",
  "purged": {
    "auditLog": 1250,
    "conversations": 84,
    "messages": 3201,
    "brainFacts": 412,
    "brainEpisodes": 967,
    "knowledgeDocuments": 58,
    "adminActionLogAnonymized": 31,
    "members": 12,
    "organization": 1
  },
  "totalRows": 5985,
  "adminActionLogAnonymized": 31,
  "skippedTables": [],
  "complete": true
}
```

The `purged` object carries a row count per table, useful for audit purposes. The example above is abbreviated — the real response includes a key for every table the purge touched (around 95 entries).

<Callout type="warn">
**`totalRows` is the count of rows DELETED, and it deliberately excludes `adminActionLogAnonymized`.** That one key inside `purged` counts rows that *survived* with their identifying columns scrubbed, so summing every value in `purged` over-reports destruction by exactly that number — in the example above, `5985` is the deleted total and naively summing gives `6016`. It is repeated as a top-level field so the distinction is visible without reading the whole map. Use `totalRows`; do not re-derive it.
</Callout>

**Always check `complete`.** When it is `false`, `skippedTables` names relations that were absent from this region's schema, whose data was **not** deleted — the purge ran, reported `0` for those tables, and is not finished. Run the region's migrations and purge again before recording the erasure as complete.

## Noisy Neighbor Detection

The noisy neighbors tab compares each workspace's resource usage against the platform median. Workspaces consuming more than **3x the median** in queries, tokens, or storage are flagged.

Each alert card shows:
- The workspace name and plan tier
- Which metric exceeded the threshold
- The actual value vs. median
- The ratio (e.g., `5.2x`)
