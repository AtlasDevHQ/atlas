Adding a source to the Company Atlas is deliberately small. The scheduling, high-water marks, incremental-versus-reconcile cadence, rate-limit backoff and per-sync caps are all shared machinery you inherit; what a new vendor writes is a client that fetches records and a declaration of what kind of evidence they are.

This page is the contract. It is written for whoever adds the next vendor — a second chat platform, a second meeting recorder, a mail provider that is not Outlook — or the first connector in a class Atlas has not shipped yet.

---

## What a vendor directory provides

A connector is one object registered against one catalog row:

```ts
interface BrainSourceConnector<S extends EpisodeSource = EpisodeSource> {
  /** The catalog row this connector serves — the dispatch key. */
  readonly catalogId: string;
  /** The source kind stamped onto every episode it produces. */
  readonly source: S;
  /** How this source's `audience:` grants stay inside the staleness bound. */
  readonly audience: BrainSourceAudienceFor<S>;
  createClient(ctx: BrainSourceInstallContext): Promise<BrainSourceVendorClient> | BrainSourceVendorClient;
}
```

Four members, and `audience` is **not optional**. It is the one a new connector is likeliest to omit: the other three are about producing episodes, and this one is about keeping the grants on them alive. [The audience declaration](#the-audience-declaration-is-required) below is what it means and how to choose an arm; [Registration](#registration) is what happens if you get it wrong.

`createClient` is handed the install row and nothing else — the workspace id, the install id, and the install's non-secret config. It may throw; a bad config or a disconnected upstream OAuth install becomes that source's error outcome with your message surfaced to the admin, so **write the message for the admin who has to fix it**, not for a log reader.

The client itself is one method:

```ts
interface BrainSourceVendorClient {
  fetchEpisodes(params: BrainSourceFetchParams): Promise<BrainSourceChanges>;
}
```

In practice a vendor directory holds four to six leaf files, and the split is worth copying: `config.ts` (identity, the stored-config shape, and the source-id contract), `api.ts` (raw vendor calls — absent for Slack, which reuses the existing Slack client), `client.ts` (the page walk and record construction), `connector.ts` (registration and credential resolution), `audience.ts` — **required** for a grant-deriving class, and absent only when something else reconciles this source's audiences (Slack is the shipped case) — `webhook.ts` for a source with a fast-path writer, plus whatever the vendor's own formats demand (Zoom has a `vtt.ts`).

`config.ts` deliberately imports nothing from the ingest core. That is what makes adding a vendor purely additive: the install handler, the connector, the audience re-verifier and the catalog seed all share one definition without any of them reaching into the engine.

## What one record looks like

```ts
interface BrainEpisodeRecord {
  readonly sourceId: string;          // THE dedupe key — see below
  readonly sourceActor: string | null; // the author at the source, or null
  readonly body: string;               // the content, stored by value
  readonly occurredAt: Date | null;    // event time at the source
  readonly visibleTo: BrainGrant;      // the derived access grant
}
```

Note what a connector **cannot** name: the episode's `id`, its `ingestedAt` and `createdAt` timestamps, and — most importantly — its `extractedAt` marker. Extraction is driven by that marker, and it must stay unset at ingest. A connector able to set it could take an episode off the extraction queue before anything extracted it, turning a visible backlog into a silent drop.

`body` is stored **by value**, not by reference. Chat is by-value on purpose: the vendor may delete the message out from under you and the evidence has to survive. It must never be empty — but that is not a type-level guarantee: the field is a plain `string`, and emptiness is refused by a database CHECK, with the ingest core dropping blank records first so one bad record cannot fail a whole batch.

<Callout type="info" title="Grant derivation is not the connector's to invent">
  Your client decides *what the vendor said about visibility* and hands it to the deriver for your class. It does not build grant tokens itself.

  Each class has its own derivation function, and the duplication is deliberate: only the chat deriver has an org-wide arm, because only a chat channel has a genuine public mode. The transcript and email derivers have no org-wide branch at all, so they cannot acquire one by accident — adding one would be a deliberate act in a function whose whole header argues against it. **A new class adds a function; it does not add a branch to an existing one.**
</Callout>

## The audience declaration is required

Deriving a grant is one job; keeping it resolving is the other, and `audience` is where a connector declares who owns it.

It is a **field on the connector** rather than a second registration call, and that shape is load-bearing. A source that mints per-object grants needs two things registered — the connector, so it ingests, and a re-verifier, so the grants it minted keep resolving. Written as two statements the first can commit and the second throw, leaving a source that ingests normally for `ATLAS_BRAIN_AUDIENCE_MAX_STALENESS_HOURS` (168h by default) and then goes **silently invisible**: its content starts reading as *not existing* rather than as denied, in a different subsystem, a week later, with nothing pointing back at boot. One field written by one registration call leaves no statement order to get wrong.

There are two arms:

```ts
type BrainSourceAudience =
  // This source mints its own `audience:` grants and brings the re-verifier that
  // refreshes them. Registered under the connector's own `source` kind, so the two
  // halves cannot be wired to different sources.
  | { readonly kind: "reverified"; readonly reverifier: AudienceReverifier }
  // Something OTHER than a registered re-verifier reconciles this source's
  // audiences, and it registers none.
  | { readonly kind: "externally-synced" };
```

Which arm you may declare is a property of your **class**, not a preference. A class whose grants are derived from the record itself — a transcript's participants, a mail's recipients — can only be refreshed by a re-verifier registered for that source:

| Connector class | Audience grain | Arm |
|---|---|---|
| `chat` | Channel-scoped, reconciled by the install-driven Slack walk | `externally-synced` (Slack's) |
| `transcript` | Per object — the meeting's own participants | `reverified`, required |
| `email` | Per object — the message's own recipients | `reverified`, required |

`BrainSourceAudienceFor<S>` is what makes that a compile-time error at a connector literal: for a per-object class it resolves to the `reverified` arm alone. **It is not the enforcement on its own** — a plugin is compiled separately and arrives as data, a cast widens past it, and so does a factory that widened its own return type — so `registerBrainSourceConnector` re-checks at runtime.

<Callout type="warn" title="`externally-synced` on a grant-deriving class is refused at registration">
  A transcript or mail connector declaring `externally-synced` does not boot degraded — `registerBrainSourceConnector` **throws**, the install step logs it at `error`, and that source ingests nothing at all.

  That is the intended outcome, and it is worth being precise about why the loud one is preferable: the half-state this seam exists to prevent is a **committed connector whose re-verifier was refused**, which is quiet for a week and then reads as missing content. A connector that never registered is fail-closed and noticed the same day.

  And `externally-synced` is a **declaration, not an opt-out**. Naming what reconciles your audiences instead — as Slack's arm names `audience/sync.ts`'s channel-roster walk — is a claim a reviewer can check, where leaving a field off was not.
</Callout>

## The stable source-id obligation

This is the one contract that is genuinely load-bearing, and the one most likely to be got wrong.

Episodes are **immutable, append-only, and deduped on `(workspace, source, source id)`**. There is no upsert and no archive — the only write is an insert that does nothing on conflict. So:

- Two writers that disagree about a record's id **duplicate it**, and nothing later converges them.
- A duplicate is not merely wasted storage. Extraction spends a model call on each copy, and fact reconciliation treats the two as *independent* evidence — so a claim gains a corroboration edge from its own echo and reads as better-supported than it is.
- Changing an id's **format** re-ingests every record in every workspace as a new episode, and re-extracts facts from all of them.

<Callout type="warn" title="The obligation, stated exactly">
  A connector's source id must be **byte-identical from every writer, on every pass, forever**. That means identical between the scheduled poll and any webhook fast-path, stable across re-fetches, and never reformatted after launch.
</Callout>

The id format is **vendor-specific by design** — there is no shared grammar to conform to, and inventing one would be worse than useless. What matters is that yours satisfies four properties. The shipped connectors are the worked examples:

| Vendor | Source id | Why that shape |
|---|---|---|
| Slack | `<channelId>:<ts>` | `ts` is the message's identity within a channel, but is **not** globally unique — without the channel prefix, two channels' messages collide and one is silently dropped |
| Zoom | `<meetingUuid>:<recordingFileId>` | The `uuid` identifies a meeting **instance**; the 11-digit meeting number identifies the series, so keying on it would collapse every occurrence of a recurring standup into one episode. The file id is needed because one meeting can hold several transcripts — stopping and restarting a recording produces one per segment |
| Outlook | The RFC 5322 `Message-ID` | It is minted once by the sending system and is **identical in every copy, in every mailbox**. Graph's own `message.id` is per-mailbox *and* re-minted on a folder move, so it would ingest one five-recipient email as five episodes and re-ingest each one when somebody archives it |

The four properties to check yours against:

1. **Unique within your source's namespace.** Not "unique at the vendor" — unique among the ids *you* mint. Slack's channel prefix exists for exactly this.
2. **Identifies the right grain.** One episode should be one piece of evidence. Zoom's instance-versus-series trap and Outlook's message-versus-thread decision are both this property.
3. **Stable across re-fetches.** Re-polling the same record must be a no-op. If the vendor re-mints an identifier when content settles, or when a user moves the item, it is not a source id.
4. **Reachable identically from every writer.** If you add a webhook path later, it must read the same values — and it will read them from a *different payload shape*.

### Where each writer reads the id from

Slack's and Zoom's `config.ts` headers each enumerate **where a writer must read the id's parts from** — Slack's because a fast-path exists today, Zoom's because one is specified against it and not yet built. Outlook has a single writer, so its trap is which *field* to read rather than which *payload*. In all three the obvious reading is the wrong one:

- **Slack** — the poll reads `message.ts`; a plain webhook event carries `event.ts`; a `message_changed` event carries the original message's id at `event.message.ts`, while its own top-level `ts` is the **event's** timestamp and `event.message.edited.ts` is the **edit's**. Reaching for either of the latter two mints a fresh id for a message already stored and duplicates every edited message — and `edited.ts` is the one a maintainer picks deliberately, thinking "I want the edit." A thread reply's `thread_ts` is its **parent**; keying on it collapses an entire thread onto one episode.
- **Zoom** — the poll reads `meeting.uuid` + `recording_files[].id`. A webhook writer must read `payload.object.*`, whose file list is pre-filtered by the event, so index 0 is not necessarily the transcript — select on the file type, through the predicate `config.ts` exports for exactly this. And `recording.completed` fires *before* the transcript exists: writing an episode from it mints the transcript's id for a file that is not there yet, which the later transcript event then dedupes against, losing the transcript permanently.
- **Zoom, again** — a meeting uuid is base64, so it routinely contains `/`, `+` and `=`. Zoom's documented rule is that a uuid *beginning with* `/` or *containing* `//` must be double-URL-encoded as a path segment; Atlas applies the encoding **unconditionally** rather than carrying a rare conditional branch that would never be exercised and would always be broken. Either way the encoding is a **transport** concern and must never reach the stored id — the poll encodes because it puts the uuid in a URL, a webhook never does because the uuid arrives in a JSON body. The id builder enforces this rather than trusting you: it refuses a value that has already been percent-encoded.
- **Outlook** — the same instance-versus-identity trap as Zoom's, with the polarity reversed, which is what makes it easy to get backwards. Graph's `message.id` is the one that *looks* canonical and is per-mailbox and per-folder; `internetMessageId` is the one that looks like a header detail and is the stable cross-copy identity. There is deliberately **no fallback** from the header to `message.id` for a message that lacks one: a fallback would restore the one-episode-per-recipient duplication for exactly the messages whose identity is already doubtful. A message with no usable header is a counted skip.

The general lesson: **build the id in one function, exported from `config.ts`, and call it from every writer.** Do not re-derive it in the webhook path.

That function is a **backstop, and it should throw** — its output is half of a dedupe key, so a malformed id does not fail loudly, it quietly lands a row nothing ever dedupes against. But a throw is the wrong tool for deciding *whether* a record is identifiable at all, which is why Outlook splits the job in two: `normalizeInternetMessageId` returns `null` and is the **gate** a caller skips on, while `outlookEpisodeSourceId` throws and is the backstop behind it. That split is what lets a message with no usable header be a counted skip rather than an exception-driven abort — and it is how the throw rule here and the [prefer-a-counted-skip rule below](#fetch-modes-coverage-and-bookkeeping) coexist without contradicting each other.

<Callout type="warn" title="Copy Zoom or Outlook here, not Slack">
  Slack's `slackEpisodeSourceId` is a bare template string with no validation and no throw. Its channel id is checked at config-parse time and its `ts` is never checked at all. It is the oldest of the three and it does **not** meet the rule this section states — so it is the worst of the shipped examples to copy, despite being the one an author reaches for first.
</Callout>

## Classes and vendors — what the stored value means

Every episode stores one `source` value, and that value carries two axes: a **class** (what kind of evidence this is) and a **vendor** (which product it came from). The class is always derived from the stored value rather than declared beside it, through one declaration per member.

The grain of the stored column is **mixed**, and that is worth seeing in full rather than inferring from the connector classes alone:

```ts
slack:     { class: "chat",       vendor: "slack"   },  // vendor-grained
zoom:      { class: "transcript", vendor: "zoom"    },
outlook:   { class: "email",      vendor: "outlook" },
warehouse: { class: "warehouse",  vendor: null      },  // class-grained
human:     { class: "human",      vendor: null      },
```

A connector class stores its **vendor**. `warehouse` and `human` come from no connector at all, so there is no vendor to name and the stored value *is* the class. Adding a member is a deliberate one-line change either way.

<Callout type="info" title="The class/vendor pairing IS compiler-checked — the class *choice* is not">
  These two are the ones people conflate, so be precise about which guarantee you have.

  The spec type is a discriminated union on `class`, not a flat `{ class; vendor: string | null }`. Vendor-ness is a property **of** the class, so two shapes are unrepresentable rather than merely discouraged: `{ class: "chat", vendor: null }` — a chat member naming no vendor, which would reintroduce the exact dedupe-namespace collision the grain exists to prevent — and `{ class: "warehouse", vendor: "snowflake" }` — a connectorless class carrying one. Neither compiles.

  What is *not* checked is whether the class you picked is the right one. See the warning below.
</Callout>

### Why a connector class stores the vendor and not the class

Because a stored value is a **dedupe namespace**. Two chat vendors both storing `chat` would put Slack's `<channel>:<ts>` ids and Teams' ids in one namespace, and a collision there does not error — it silently drops one vendor's message as a duplicate of the other's.

Email is the case that looks like an exception and is not, so it is worth spelling out. Email *does* have a genuinely cross-vendor identifier: a `Message-ID` is the same in every copy of a message, so an Outlook connector and a Gmail connector would mint identical ids for the same mail. That looks like free deduplication, and one shared stored value looks correct.

It is not, because the stored value does more than dedupe. It is what every downstream discriminator reads, it is the scan key the audience re-verifier walks on, and it is what routes a correction. Two vendors sharing it means **one vendor's re-verifier walking the other's audiences holding the wrong credential**. The id collision being benign is a different claim from the source being shared, and conflating them turns a dedupe convenience into a cross-vendor access fault.

So: a new vendor within an existing **connector** class is a **new member**, not a reuse. A new class arrives with its first connector, in the same change.

The class-grained members invert that, and it is worth stating because following the rule above literally would get it wrong: for a warehouse-shaped producer, **prefer the existing `warehouse` value** even when the producer is vendor-specific. Put the vendor identity in the catalog id and in the fact's producer field instead — one stored value per class is one dedupe namespace fewer to reason about. A separate stored value is warranted only if that vendor's source-ids would otherwise collide, which is the same test the chat class passes and the reason it is vendor-grained at all.

<Callout type="warn" title="One rule the compiler cannot check for you">
  If the kind you are adding is warehouse-shaped, it **must** declare the warehouse class. Warehouse-derived facts are refused a hand-correction path — the fix belongs in your data or your semantic layer, not in an override the next sync overwrites — and that refusal keys off the class alone.

  Nothing in the type system knows what "warehouse-shaped" means. `{ class: "chat", vendor: "snowflake" }` compiles cleanly and escapes the refusal entirely. What the single declaration buys is that the producer and the refusal can no longer *disagree* about which value means warehouse. Choosing the right class is still a judgement call, and it is the one this change exists to make you confront.
</Callout>

## Fetch modes, coverage, and bookkeeping

`fetchEpisodes` receives a mode, a `since` mark, an opaque cursor, and a hard cap on how many episodes this pass may return.

- **`incremental`** — fetch what changed since `since`.
- **`reconciliation`** — the wider-window cadence. It is **not** a full enumeration, and nothing is archived from its absences. That half of the shared engine scopes to documents, not episodes. On the episode side the cadence is repurposed to **re-run extraction**; widening your own fetch window is optional on top of that, and a source with nothing wider to fetch may treat this mode identically to `incremental` — the Slack source does.

`since` is the persisted high-water mark **minus an overlap window**, so you will re-fetch some records. That is intentional and free: re-fetched records no-op in the source-id dedupe, so the overlap costs bandwidth and never correctness. It is also the property that lets the incremental window be rewound safely.

`maxEpisodes` is required rather than optional, and it is the *effective* cap — the smaller of the platform ceiling and the workspace's plan tier. Honour it. A client that fell back to the raw platform ceiling would burn a small workspace's vendor rate limit pulling many times what it can ever ingest.

Return the bookkeeping honestly:

| Field | Contract |
|---|---|
| `highWaterMark` | The newest **source-side** event time this fetch covered. Return the source's clock, never the local one. `null` when nothing new was covered |
| `cursor` | Opaque, persisted verbatim, echoed back next pass |
| `coverageIncomplete` | `true` when you *know* this pass left part of its window uncovered while the records you returned are sound |
| `warnings` | Non-fatal notes — a channel that exceeded its budget, a sub-source the vendor refused — surfaced in the sync report so a partially-covered success is never silently green |

<Callout type="warn" title="`coverageIncomplete` puts the correctness burden on you, not the engine">
  When you report incomplete coverage the engine still ingests your records and still advances the high-water mark **you returned** — it only holds the reconcile clock so the wider re-crawl stays due.

  So a client reporting incomplete coverage must return a mark (and cursor) covering only the **contiguous** part of the window it actually enumerated. Return the newest thing you saw across a gapped walk and you will skip the gap forever.
</Callout>

Throwing is fine and is isolated per source — a rate-limit error from the shared throttle vocabulary gets the engine's bounded backoff; anything else becomes that source's error outcome and never fails the cycle. But prefer a **counted skip** to a throw for permanent per-record conditions. A message with no usable identifier is skipped, counted, and its window still marked covered, because a header a message does not have will never appear on a retry, and retrying it forever freezes the cursor.

## Registration

Register once, at wiring time. Registration fails loudly, and never halfway — every one of these throws with nothing written to any registry:

| Refusal | What it would otherwise cost |
|---|---|
| A duplicate catalog id | A silent overwrite, letting one source shadow another's installs |
| A malformed source slug | Unqueryable garbage in `brain_episodes.source` |
| A kind outside the vocabulary | A value no downstream discriminator recognises, making every fact derived from it uncorrectable |
| A malformed `audience` declaration | A re-verifier registered as `undefined`, which then fails on every cycle forever |
| **A grant-deriving class that declared no re-verifier** | The 168h-then-invisible decay above |
| A re-verifier already held for this source | Two of them reconciling against their own rosters, each revoking the loser's members every cycle |
| **A catalog id already claimed by the knowledge-document registry** | Two ingest targets for one catalog id |

The last is the one a new author is likeliest to trip. One catalog id has exactly one ingest target, and both registries claim through a shared module so the check is order-independent rather than depending on which registers first.

That "never halfway" is a property of how the function is arranged, not a promise: registration writes three process-global structures, and no `catch` outside it can undo a write, so every throw site sits **above** the first write.

The vocabulary check exists at runtime as well as in the type system, because a plugin-shaped connector is compiled separately and arrives as data rather than as a checked type. At registration an unrecognised kind simply **throws** — no such connector ever produces an episode.

There is a separate, narrower lane where an unrecognised kind *can* reach storage, and it is worth not confusing with the above: a region import restores a bundle's stored `source` verbatim so that a bundle written by a newer vocabulary still imports. Facts carrying a kind this deployment cannot classify are **correction-quarantined** rather than silently treated as ordinary — and deploying the vocabulary that knows the kind releases them, with no data migration.

## Before you ship

- [ ] The source id is minted by **one exported function**, called from every writer.
- [ ] That function throws on a malformed input rather than returning a sentinel.
- [ ] Its `config.ts` header enumerates the field paths each writer reads the id's parts from.
- [ ] Transport encoding never reaches the stored id.
- [ ] The new member declares its class, and the class is the right one.
- [ ] The grant deriver is your class's, and a class new to Atlas got its own function rather than a new branch.
- [ ] `audience` is declared, and its arm matches your class — `reverified`, with the re-verifier, for a per-object class. Registration refuses the connector otherwise.
- [ ] "The audience could not be established" blocks; "the audience contains no Atlas users" does not.
- [ ] `coverageIncomplete` is paired with a contiguous high-water mark.
- [ ] Permanent per-record failures are counted skips, not throws.
- [ ] Install-form errors name the field an admin has to fix.
- [ ] Any new configuration knob is in the settings registry, not only an environment variable.
