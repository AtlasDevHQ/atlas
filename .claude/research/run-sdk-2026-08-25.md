## Bottom line

**Verdict: WATCH.** Do not adopt now; do not dismiss it either. The package is genuinely well-built —
better than three weeks of repo age suggests — but Atlas has no workload it fits today, and three of the
findings below are hard blockers rather than preferences.

The five facts that drive it:

1. **Atlas has no JavaScript-execution seam, and the existing sandbox abstraction cannot hold one.**
   `ExploreBackend` is `exec(command: string) → { stdout, stderr, exitCode }`
   (`packages/api/src/lib/tools/backends/types.ts:30-33`); `PythonBackend` is
   `exec(code, data?) → PythonResult` (`packages/api/src/lib/tools/python.ts:287-295`). Both are
   *string-in, text-out*. `run` is *source + typed host functions in, structured value or interruption
   out*. It does not implement either interface. §2.
2. **We already ship QuickJS and never start it.** `quickjs-emscripten@0.32.0` plus all four
   `@jitl/quickjs-wasmfile-*@0.32.0` WASM variants are in `bun.lock` (lines 3653, 1487-1495),
   transitively via `just-bash@3.1.0`. They are dead weight: `js-exec` is a lazily-`import()`ed chunk
   that only registers when `javascript` is configured, and Atlas's single `Bash` construction
   (`packages/api/src/lib/tools/explore.ts:74-81`) does not configure it. §1.
3. **The AI SDK route — the nearer path, since Atlas already runs the AI SDK agent loop — is
   version-blocked.** `@ai-sdk/code-mode` (the wired-in consumer of `run`) peer-pins `ai: 7.0.79`.
   Atlas is on `ai: ^6.0.235` (`packages/api/package.json:78`). npm dist-tags: `latest 7.0.79`,
   `ai-v6 6.0.266`. Code mode needs a v6→v7 major upgrade before it is even reachable. §5.
4. **The default continuation token is signed but *not encrypted*, and it embeds every host-function
   argument and result verbatim.** The docs say it outright: *"The default signed continuation protects
   integrity but does not encrypt its contents. Base64 is not encryption."* For a text-to-SQL agent
   whose host functions would return query result **rows**, that is a direct collision with the
   "No secrets in responses" invariant. §4.
5. **Atlas deliberately chose append-and-continue over replay, and `run` is replay.** ADR-0020's
   "Considered and rejected" list rejects re-running a turn because it *"re-executes side-effecting
   tools"*; its resume re-enters `streamText` with the stored transcript so the model **continues**.
   `run` resumes by re-executing the source from the top against a recorded ledger. Both models are
   sound; running both in one request means two resume mechanisms with opposite failure modes, and
   `run`'s interruptions duplicate the approval-park that ADR-0020 phase 3 already shipped. §3.
6. **The nearest "replace something we already do" case was measured and does not exist.**
   `executePython` has **never been registered in production** — the prod `api` service sets neither
   `ATLAS_PYTHON_ENABLED` nor `ATLAS_SANDBOX_URL`, and
   `lib/tools/python-sandbox-requirement.ts:1-53` makes that pair a hard registration contract. Zero
   `executePython` occurrences across all three regional DBs. There is no code-execution workload to
   migrate; `run` in Atlas would be net-new or nothing. §6b.

**What the package is worth, in one line** (§6b.3): its value is the *additive* capability model — the
guest starts with nothing and gets exactly the host functions passed — and it pays off in proportion to
how much multi-tool orchestration you do per turn. Atlas is SQL-in / answer-out, so today that is ~zero.

What would flip this to *adopt*: AI SDK v7 landed in Atlas, **and** a real product need for the model to
orchestrate several tool calls in one step, **and** Bun's `worker_threads.terminate()` becoming reliable
(today `run` bounds it at 100 ms because it can hang mid-WASM). All three, not any one.

# Part I — What this means for Atlas

## 1. The `just-bash` collision

### 1.1 What Atlas actually uses `just-bash` for — one import, one construction

`grep -rn "just-bash"` across `packages/ apps/ examples/ plugins/ deploy/ scripts/ docs/ .claude/`
returns 172 non-test hits across 50 files, but they are almost entirely *prose*: doc pages, config
enumerations, health-check strings, log messages, ADR text. There is exactly **one** import in the
entire tree:

```
packages/api/src/lib/tools/explore.ts:59:    ({ Bash, OverlayFs } = await import("just-bash"));
```

and exactly one construction, ten lines below it:

```ts
// packages/api/src/lib/tools/explore.ts:71-81
const overlay = new OverlayFs({ root: semanticRoot, mountPoint: "/semantic" });
const bash = new Bash({
  fs: overlay,
  cwd: "/semantic",
  executionLimits: { maxCommandCount: 5000, maxLoopIterations: 1000 },
});
```

Its whole job is: **a simulated bash shell over a read-only overlay of the semantic-layer directory**,
so the `explore` tool can let the agent `ls`/`grep`/`awk` its way through entity YAML. The backend
returns `{ stdout, stderr, exitCode }` (explore.ts:82-90) and nothing else. It is the bottom of the
sandbox priority chain — `plugin > vercel-sandbox > nsjail (explicit) > sidecar > nsjail (auto) >
just-bash` (explore.ts:12) — and selecting it logs **`SECURITY DEGRADATION: Explore tool running without
process isolation (just-bash fallback)`** in production (explore.ts:426-434 and again at :722-730). It
is classified `"just-bash": "unsandboxed"` in the compile-checked isolation table
(`packages/api/src/lib/tools/backends/selection.ts:499-504`), and SaaS pins
`sandbox.priority: ["vercel-sandbox"]` with no `just-bash` member, so on SaaS it is unreachable by
construction (`.claude/rules/api-security-general.md:15`).

Version: pinned **exactly** at `just-bash@3.1.0` (`packages/api/package.json:94` — no caret) and
resolved to `just-bash@3.1.0` in `bun.lock:3111`. It is one of the packages CLAUDE.md requires to stay
in `serverExternalPackages`, and it is there: `packages/web/next.config.ts:47`.

*(Housekeeping, not a defect: `node_modules/just-bash/package.json` in this checkout reads `3.0.2` while
the pin and the lockfile both say `3.1.0` — a stale local install. `bun install` fixes it. It does not
affect any conclusion here; all just-bash facts below were read from a freshly-`npm pack`'d 3.1.0
tarball, not from `node_modules`.)*

### 1.2 Is `js-exec` still in our pinned version? Yes — untouched.

Downloaded and unpacked `just-bash@3.1.0` from the registry. `js-exec` is present and shipping:

- `package/dist/commands/js-exec/js-exec.d.ts` and `js-exec-worker.d.ts`
- built chunks at `package/dist/bundle/chunks/js-exec-SR6IMNWM.js`,
  `package/dist/bin/chunks/js-exec-F7JAZ4ZQ.js`, `package/dist/bin/shell/chunks/js-exec-F7JAZ4ZQ.js`,
  `package/dist/commands/worker-bridge/…`
- documented in `package/README.md` §"Optional Runtimes" (line 73), §"Node.js Compatibility" (360-371),
  §"Tool Invocation Hook" (373-392)
- referenced as a **live** capability in `package/CHANGELOG.md` 3.1.0's own entry: *"could not enable
  python3, js-exec, a restricted command set … even though the runtimes ship in the package"*, and the
  behaviour note *"Python/js-exec stay off"* by default.

Not deprecated. Not removed. Not marked legacy. `just-bash@3.1.0`'s `dependencies` include
`quickjs-emscripten: ^0.32.0` **directly**, and do **not** include `run`.

### 1.3 Are we already running a QuickJS sandbox without calling it that? No — we ship one and never start it.

Two facts settle this.

**We ship it.** `bun.lock` carries `quickjs-emscripten@0.32.0` (line 3653), `quickjs-emscripten-core`
(3655), `@jitl/quickjs-ffi-types` (1487) and all four WASM variants — `wasmfile-debug-asyncify` (1489),
`wasmfile-debug-sync` (1491), `wasmfile-release-asyncify` (1493), `wasmfile-release-sync` (1495). Every
one of those is in the tree solely because `just-bash` depends on it.

**We never start it.** The `js-exec` command is not statically linked into just-bash's entry bundle. In
`dist/bundle/index.js` it appears only inside a lazy registration list:

```js
Ts.push({ name: "js-exec", load: async () => (await import("./chunks/js-exec-SR6IMNWM.js")).jsExecCommand });
Ts.push({ name: "node",    load: async () => (await import("./chunks/js-exec-SR6IMNWM.js")).nodeStubCommand });
```

and the published type declarations gate that list explicitly:
*"JavaScript command names (**only available when javascript is explicitly enabled**)"* —
`package/dist/commands/registry.d.ts:8-9`, with `createJavaScriptCommands()` documented as *"only
registered when javascript is explicitly enabled"* (registry.d.ts:44-48). Atlas's `new Bash({...})` at
explore.ts:74-81 passes `fs`, `cwd` and `executionLimits` and **no `javascript` key**, so the chunk is
never `import()`ed and the QuickJS WASM is never instantiated.

Practical consequence worth stating, because it cuts the other way too: an agent running arbitrary shell
in the `explore` tool **cannot** reach `js-exec` or the `node` stub to escape into JS. Those commands do
not exist in our registry. That is a real (if accidental) property of the current configuration, and it
would change the moment anyone passed `javascript: true` — which nothing in the tree does.

### 1.4 Does the extraction imply anything for our pin?

**No.** Concretely:

- **No deprecation.** Nothing in `just-bash@3.1.0`'s README, CHANGELOG, or type declarations marks
  `js-exec` as legacy, and `just-bash` does not take a dependency on `run`.
- **No breaking change.** `just-bash`'s latest is `3.4.2` (`npm view just-bash --json`); we are pinned at
  `3.1.0`. Whatever drift exists between them is ordinary version drift, unrelated to `run`.
- **Some dead weight, and it predates all of this.** ~1 MB of QuickJS WASM variants ride in the install
  because `just-bash` hard-depends on `quickjs-emscripten` rather than making it optional. That is a
  pre-existing install-size cost, not a consequence of the extraction, and it is the *only* thing in
  this section that is even mildly actionable — and only upstream, in `just-bash`.
- **The extraction claim itself does not survive verification** (§8). So there is nothing to plan
  around.

**Net: our `just-bash` pin needs no change on account of the Run SDK.**

## 2. Where a Run-SDK seam would go — and why it does not fit the existing abstraction

### 2.1 The two interfaces a backend must satisfy today

Sandbox selection is one shared, pure policy module,
`packages/api/src/lib/tools/backends/selection.ts`, feeding two tools with *different* backend
interfaces:

```ts
// packages/api/src/lib/tools/backends/types.ts:22-33
export interface ExploreBackend {
  exec(command: string): Promise<ExecResult>;   // ExecResult = { stdout, stderr, exitCode, ...Truncated? }
  close?(): Promise<void>;
}
```

```ts
// packages/api/src/lib/tools/python.ts:287-295
export interface PythonBackend {
  exec(code: string, data?: { columns: string[]; rows: unknown[][] }): Promise<PythonResult>;
  execStream?(code, data, onProgress: (e: PythonProgressEvent) => void): Promise<PythonResult>;
}
```

The plugin boundary re-exports the explore one: `AtlasSandboxPlugin.sandbox.create(semanticRoot) →
PluginExploreBackend` (`packages/plugin-sdk/src/types.ts:1163-1178`), with built-in priorities
documented as `vercel=100, nsjail=75, sidecar=50, just-bash=0` and plugin default 60
(plugin-sdk/src/types.ts:1174-1175).

### 2.2 `run` does not implement either — and the mismatch is structural, not cosmetic

| | `ExploreBackend` / `PythonBackend` | `run` |
|---|---|---|
| Input | one opaque **string** (shell command / Python source) | source **+ a typed `hostFunctions` map** the guest calls by name |
| Output | `{ stdout, stderr, exitCode }` / `PythonResult` | `{ status: 'completed', value }` \| `{ status: 'interrupted', interruptions, continuation }` |
| Capability model | ambient — whatever the sandboxed OS image provides | **deny-by-default**: nothing exists but the host functions you pass |
| Failure | non-zero exit code, in-band | promise **rejection** with a `RunError` subclass |
| Statefulness | stateless per `exec` | stateless per run, but **resumable** via a continuation token |

You cannot wrap `run` in `exec(command: string)` without throwing away the entire point of it — the
typed host-function boundary. A `run`-shaped backend would be **a third interface**, not a fourth
implementation of an existing one. Correspondingly it would not be a new *backend*; it would be a new
*tool* (`executeJs`, or a code-mode orchestration layer) registered in
`packages/api/src/lib/tools/registry.ts` alongside `explore`/`executeSQL`/`executePython`.

### 2.3 If it were added as a backend name anyway — the exact blast radius

Suppose someone did add `"run"` to `SANDBOX_BACKEND_NAMES` to make it operator-selectable. The type
system forces a specific, countable set of edits. These are the sites, each read:

## 3. Durable sessions vs. Run's replay

Atlas already has a resume story. It is not the same one, and the difference is deliberate.

### 3.1 What Atlas does today

ADR-0020 (`docs/adr/0020-durable-agent-sessions.md`) — Accepted 2026-06-17, phases 1–3 shipped:

- **Grain:** one *run* = one user turn = exactly one `agent_runs` row, advanced **in place**
  (`packages/api/src/lib/durable-session.ts:5-14`). `recordRunCheckpoint` (`:280`) upserts a `running`
  checkpoint at each step boundary with a monotonic step index; `recordTerminalAgentRun` (`:293`) flips
  the same row to `done`/`failed`; `recordParkedAgentRun` (`:310`) parks it.
- **What is stored:** the accumulated `ModelMessage[]` transcript as JSONB. ADR-0020: *"completed tool
  calls are already in the messages array, so the model **continues** rather than re-executing them."*
- **Resume:** `loadAndLeaseResumableRun(conversationId, leaseSeconds)`
  (`durable-session.ts:508-560`) atomically claims the row with a `resuming_lease` +
  `resuming_lease_owner`, returns `{ runId, orgId, stepIndex, transcript, leaseOwner }`, and **fails
  closed** on any DB error — its own comment: *"a transient DB blip can't be allowed to silently start a
  second concurrent stream"* (`:552-556`). Single-flight is enforced by that lease
  (`releaseResumeLease` at `:647`, default TTL 300 s at `:80`).
- **Approval-park:** `loadParkedRunByApprovalRef(approvalRequestId)` (`:720`) and
  `resolveParkedRun` (`:806`) — the resolver **rewrites** the needs-approval tool result in the stored
  transcript and flips `parked → running`. Max park 1440 min (`:70`), swept by a retention fiber.
- **Working memory** is a *separate* substrate: `defineDurableState` handles over named slots in
  `agent_session_memory`, keyed on **`conversation_id`, not `agent_runs.id`** — per session, not per
  turn (`packages/api/src/lib/durable-state.ts:402`, `:448` `loadSessionMemory`, `:477`
  `commitSessionMemory`, `:528` `buildDurableStateStore`, `:606` `renderDurableMemoryBlock`). Subagents
  are forced onto a Noop store so nothing crosses the parent/child boundary.
- **Compaction** (`packages/api/src/lib/agent-compaction.ts`) rewrites the **message array** only —
  `shouldCompact` (`:396`), `pinBoundaryIndex` (`:413`), `compactOlderHistory` (`:451`),
  `summarizeIncremental` (`:651`). ADR-0020 records that working memory lives in the *system* prompt
  precisely so compaction is structurally unable to evict it.

### 3.2 What `run` does

Resume re-executes the **source from the top**, feeding recorded outcomes back from a ledger. Settled
host functions are **not** re-called; only the interrupting one is re-entered, with
`context.resume = { interruptionId, payload, resolution }`. Guest `Date`/`Math.random` are replaced with
seeded deterministic implementations so the program re-walks the same path. Divergence — a different
host-function name or different serialized arguments at any ordinal — is a hard
`RunProtocolError('Continuation replay diverged from the recorded host function ledger.')`. Full
mechanics in §7.

### 3.3 Compose, duplicate, or fight? — one of each

**It DUPLICATES approval-park.** This is the sharpest overlap. ADR-0020 phase 3 shipped exactly the
"pause for a human decision, release the compute, resume later" capability, keyed on the EE approval
queue, with `parked_reason` carrying the queue id and a DB CHECK making a reason-less parked row
unrepresentable. `run`'s `context.interrupt(payload)` → `RunInterruptedResult` → resolution → resume is
the same capability one level down. A gated `executeSQL` reached *through* a code-mode host function
would park twice: the inner `run` interruption suspends the program, and the outer `agent_runs` row
parks the turn. Two park records, two expiry clocks (Run's default continuation `maxAgeMs` is 1 hour;
Atlas's `DEFAULT_MAX_PARK_MINUTES` is 1440), two resolvers. There is no version of that which is not a
correctness hazard.

**It FIGHTS the durability model.** ADR-0020's "Considered and rejected" contains, verbatim:
*"Re-run the whole turn from the user's last message on failure (status quo). Rejected as the target …
Re-running re-pays for every completed model step and tool call and **re-executes side-effecting
tools**."* Atlas chose append-and-continue precisely to avoid replay. `run`'s replay is *safe* — the
ledger suppresses re-execution, which is the thing Atlas could not do at the transcript level — but it
is still the opposite mental model, and a request that carried both would have two resume paths with
inverted assumptions about whether re-entering code is safe.

**It COMPOSES on storage and scope, cleanly.** Two real fits:

- `createStoredContinuationCodec({ storage })` takes a `ContinuationStorage` interface —
  `set` / `acquire(key, claimId)` / `consume(key, claimId)` / `release(key, claimId)`, with a claim-id
  transaction so a failed decode rolls back. That is *structurally the same shape* as
  `loadAndLeaseResumableRun`'s `resuming_lease` + `resuming_lease_owner` single-flight claim
  (`durable-session.ts:508-560`). Atlas's internal Postgres could implement it directly, and the
  fail-closed discipline would transfer.
- `continuationContext` binds a run to serializable tenant/principal/policy data and is folded into the
  scope hash. `{ orgId, userId }` maps onto it exactly. **But** note ADR-0020's invariant: *"A resume
  re-binds `RequestContext` + `AuthContext` from the stored actor and re-resolves the connection,
  whitelist, and RLS filters **fresh at resume time** — never from the checkpoint."* That is compatible
  with `run` only because the scope hash **rejects** on mismatch rather than **granting** on match — and
  Run's own docs agree: *"Scope validation does not authorize the person submitting a resolution."*

**Where compaction lands:** nowhere good. `run`'s continuation holds the *program's* ledger, which
compaction never sees and could not summarize if it did (the ledger is a wire format with byte-exact
replay matching). A long-parked code-mode run whose surrounding turn got compacted would resume against
a transcript that no longer describes how it got there. Not fatal — the two are independent — but it is
a second unbounded store on the same conversation with no shared retention policy.

## 4. Invariant collisions

Tested against CLAUDE.md's "Product invariants", `.claude/rules/api-sql-security.md`,
`.claude/rules/api-security-general.md`, and CLAUDE.md's error-handling rules.

### 4.1 SELECT-only, single-statement, whitelist-scoped SQL — **PRESERVED, if and only if the host function is `executeSQL` itself**

Where the gate actually lives: `validateSQL` in `packages/api/src/lib/tools/sql.ts:630`, built on a
single shared AST parse (`parseOnce`, `sql.ts:200`). Per `.claude/rules/api-sql-security.md:14`: *"All
SQL parsed via `node-sql-parser` … **exactly once** per validation … the shape guards, the
forbidden-function AST walk, the table whitelist, and the query classifier all read that same parse."*
Unparseable queries are **rejected**, never skipped.

That gate is host-side and already shared: `validateSQL` is imported by **10 modules outside `sql.ts`** —
`api/routes/validate-sql.ts:18`, `api/routes/dashboards.ts:3150`, `lib/dashboards.ts:1350`,
`lib/tools/create-dashboard.ts:54`, `lib/tools/bound-dashboard.ts:38`,
`lib/semantic/expert/amendment-validation.ts:249`, `lib/brain/warehouse-producer.ts:4945` — every one a
dynamic-or-static import of the same function. There is no second validator.

**A code-mode sandbox would not move or bypass this gate.** The guest cannot reach a database: it has no
`fetch`, no `net`, no `fs`, no `process`, and nothing but the host functions handed to it. A host
function that wraps the existing `executeSQL` tool inherits `validateSQL` unchanged. Run's own docs make
the same point from their side: *"host functions remain trusted application code … A broad host function
grants broad authority."*

**The real risk is host-function design, and it is not hypothetical.** A convenience host function that
took a *table name*, a *connection id*, or a *filter fragment* and built SQL host-side would sidestep
nothing structurally — the built string still goes through `validateSQL` — but a host function that took
a **raw SQL string and a connection id and called the driver directly** would. `warehouse-producer.ts`
already had to learn this lesson: its comment at `:4915` calls the check *"The shipped SQL gate — the
product's own `validateSQL`, on the BUILT statement"*, and `:1680` records that moving `validateSQL` out
of the runner *"stopped a substituted RUNNER"* from skipping it. Any code-mode host-function surface
would need the same discipline, enforced by review, because **nothing lints for it**.

### 4.2 No secrets in responses — **COLLIDES, on the default codec**

`.claude/rules/api-security-general.md:12`: *"Never expose connection strings, API keys, or stack traces
to the user or agent."*

Run's default `createSignedContinuationCodec` produces
`base64url(canonical JSON({ …, state: { source, ledger, … } })) + "." + HMAC-SHA256`. The ledger holds
`inputJson` and `valueJson` for **every** host-function call (§7.1). For a data agent, `valueJson` is
*query result rows*. The token is handed to the caller as a resumable handle. Base64url is not
encryption — and the docs say precisely that:

> *"The default signed continuation protects integrity but does not encrypt its contents. Base64 is not
> encryption, so keep sensitive data out of source, host function arguments, interruption payloads, and
> continuation context."*
> — [interruptions.mdx:67-70](https://github.com/vercel-labs/run/blob/main/content/docs/foundations/interruptions.mdx)

The type declaration calls it `/** Opaque bearer capability. */` (types.ts:128). **Opaque is not
confidential.** Contrast Atlas's own posture: integration credentials are versioned AES-256-GCM at rest
(`.claude/rules/api-security-general.md:14`), and the Python sandbox path carries an explicit
`scrubErrorDetail` hook so a provider 401 echoing a rejected key never reaches operator logs
(`packages/api/src/lib/tools/python-sandbox.ts:62-70`). Emitting result rows in a readable token would
be a step backwards from both.

**Mitigation exists and would have to be mandatory, not default:** `createStoredContinuationCodec` makes
the token a 43-char random key with state in Atlas's own storage. If `run` is ever adopted, "signed codec
forbidden" is a gate, not a preference.

### 4.3 Readonly DB connections — **UNAFFECTED**

The guest never holds a connection. `ConnectionRegistry` stays host-side, and readonly enforcement
(PostgreSQL via validation, MySQL via session variable, ClickHouse via `readonly: 1`) is untouched. No
exposure.

### 4.4 Error-handling rules — **MOSTLY ALIGNED, one friction point**

CLAUDE.md requires: never silently swallow; type-narrow caught errors; request IDs on all 500s; prefer
errors over silent fallbacks.

- **Aligned:** `run` *rejects* rather than returning an error status — there is no `status: 'failed'`
  variant to accidentally ignore (§6.1). Its stable codes (`RUN_TIMEOUT`, `RUN_BRIDGE_LIMIT`,
  `RUN_PROTOCOL_ERROR`, …) map cleanly onto Atlas's "no generic error messages" rule.
- **Friction:** the sandbox refuses to run host functions it cannot serialize, so a host function that
  returns a class instance fails at the boundary rather than degrading — good — but Atlas's tools
  currently return AI-SDK-shaped structured results that would need an explicit serializable projection.
- **Watch item:** `run`'s own trust path contains bare `catch {}` blocks (the guest hardening prelude
  uses ~6, and `destroyWorker` swallows terminate failures at manager.ts:1285-1287). Those are upstream
  code and would not violate our lint, but they are in the isolation boundary.

### 4.5 Explore is read-only *by isolation* — **a different story, not a weaker one**

`.claude/rules/api-security-general.md:11`: *"Each explore backend is read-only **structurally** …
there is no command allowlist or `semantic/`-scoped path check."* A `run`-based tool would be read-only
*by capability* instead: nothing is reachable but the host functions passed in. That is arguably a
stronger claim than the shell backends make — but it is a **different** claim, and every operator-facing
surface that reports isolation posture (`BACKEND_ISOLATION` at selection.ts:499, `/api/health`'s
`isolated` / `isolationVerified`, `startup.ts`'s boot log) would need it re-derived rather than
inherited. See the §2.3 table.

## 6. Verdict, and the cost of being wrong

**WATCH.** Concretely:

- **Do not** add `run` to `packages/api` now. No seam (§2), code mode blocked on AI SDK v7 (§5), Bun
  support one day old with a documented workaround around an upstream hang (§9.3).
- **Do** revisit when Atlas moves to AI SDK v7 — at that point `@ai-sdk/code-mode` becomes a
  ~one-dependency experiment rather than a subsystem, and the tool→hostFunction mapping is already
  written upstream.
- **If** it is ever adopted, three things must be true from day one: (a) `createStoredContinuationCodec`
  backed by the internal DB — the signed codec is forbidden by §4.2; (b) `continuationContext` carries
  `{ orgId, userId }` **and** the resume path authenticates independently of the token, per Run's own
  warning and ADR-0020's re-resolve-fresh invariant; (c) it registers as a **tool**, not a
  `SandboxBackendName`, so the §2.3 blast radius stays at zero.
- **Cost of being wrong in the "watch" direction** is low: the package is Apache-2.0 with zero runtime
  dependencies and can be adopted later at the same price. **Cost of being wrong in the "adopt"
  direction** is a second durability mechanism inside a request that already has one (§3.3), which is
  the expensive kind of mistake.
- **Free take-away regardless:** `run`'s guest hardening prelude
  (`packages/run/src/runtime/guest-sources.ts:45-165`) is a good reference for what a JS sandbox must
  delete, freeze and redefine, and its ledger-divergence check is a better replay-safety pattern than
  most. Worth reading even if nothing is adopted.

## 6b. What `run` is *for* — and a measured check that killed the nearest Atlas use case

Added after the main investigation, from a follow-up measurement against prod and an assessment of
intent. The §6 verdict (WATCH) is unchanged; this section removes one candidate rationale for it and

### 6b.1 Measured: `executePython` has never run in production

A "light post-SQL transforms could move from `executePython` to `run`" idea was floated in discussion.
It is **dead**, and not marginally — the workload does not exist.

Queried the three regional internal DBs directly (`railway ssh --service <region>-int-postgres`,
project `satisfied-creation`, environment `production`, 2026-08-25). Read-only `SELECT count(*)`:

| Region | `messages` | containing `executePython` | `agent_runs` | containing `executePython` |
|---|---|---|---|---|
| `us-int-postgres` | 131 | **0** | 0 | 0 |
| `eu-int-postgres` | 0 | 0 | 0 | 0 |
| `apac-int-postgres` | 0 | 0 | 0 | 0 |

23 conversations total, all US. **The cause is structural, not incidental.** The prod `api` service

Two independent reasons the migration idea was wrong even in principle:

1. **The prompt steers trivial work away from Python already.** `registry.ts:198`: *"Do NOT use
   executePython for simple aggregations, GROUP BY, or filtering — executeSQL handles those."* The
   transforms imagined as migratable are ones Atlas deliberately routes to SQL.
2. **Python ≠ JS.** The tool's contract is pandas/matplotlib-shaped (`_atlas_table`, `_atlas_chart`,

empty, is a **near-empty prod**. This is "no usage data yet", not "measured demand and it is low". No

conclusion is the structural one: the tool is not registered, so it is not a migration source.

**Incidental finding worth its own line:** prod is running with no Python tool at all. Whether that is
intended is outside this note's scope, but it is not obvious from the deploy config and nothing in the
tree flags it.

### 6b.2 What Vercel appears to be building it for

Inference from artifacts, not from any Vercel statement — labelled as such.

- **It is a consolidation, not a new product.** [vercel/ai#18832](https://github.com/vercel/ai/pull/18832)
  is **+978 / −4428** across 36 files (§9.5). They deleted a sandbox already written inline in the AI SDK
  and replaced it with a dependency. Code mode is `run`'s reason to exist; the standalone package is the
  by-product.
- **It fills a gap in their own ladder.** `eval` (no boundary) → *nothing* → Vercel Sandbox (real VM,
  provisioned, billed). `run` is the cheap middle, and their README routes anything needing an OS,
  package installation, or process isolation *up* to Vercel Sandbox (§9.5). Free OSS primitive at the
  bottom, paid product at the top.
- **The interrupt/resume machinery is overbuilt for "safe eval" and correctly built for agent
  approvals.** The PR's own future work is *"attach tool approvals to the `run` mechanism"*, and code
  mode does **not** yet integrate with AI SDK tool-approval flows (§9.5). That is the direction of
  travel.

### 6b.3 What it is actually worth

- **The capability model is the valuable part, not the sandbox.** Container isolation is *subtractive* —
  start from an OS, remove things, hope nothing was missed. `run` is *additive*: the guest starts with
  nothing and receives exactly the host functions passed (§9.2 — `fetch`, `fs`, `process`, `eval`,
  timers, `import()` are absent, not disabled). Auditing authority becomes reading one object literal.
  This is why their only substantive caveat is *"a broad host function grants broad authority"*.
- **It changes the economics of model-authored programs.** At no infra cost and no provisioning, one
  model response can fan out several tool calls, join and filter in-guest, and return the answer instead
  of the rows. That is the answer to context bloat and MCP tool sprawl.
- **It is not a strong security boundary, by its own docs** — *"not a container, a virtual machine, or a
  separate operating-system process"* (§9.2) — and five escape-class fixes landed after first publish in
  a three-week-old repo (§9.1). Capability confinement for code *your own model* wrote; not a place to
  run code from strangers.
- **Replay taxes host-function design permanently** (§7.3). Elegant, but inherited forever.
- **Almost all of its value should be consumed through `@ai-sdk/code-mode`, not directly.** Using `run`
  raw means re-writing the tool→hostFunction mapping #18832 already wrote (§5).

**For Atlas specifically:** the worth of `run` is a function of multi-tool-orchestration-per-turn. Atlas
is SQL-in / answer-out, and its one code-execution tool is not registered in prod (§6b.1). That is not a
criticism of `run` — Atlas simply does not have the workload it makes cheaper. §6's WATCH stands, now on
firmer ground.

# Part II — The upstream facts (the evidence)

## 7. Replay, precisely

### 7.1 The continuation state

`RunContinuationState` (types.ts:157-168): `{ version: 2, runtime: 'run-replay-v2', serde: 'run-js-v1',
source, logicalRunId, scopeHash, determinism, ledger }`. `RunLedgerEntry` (types.ts:186-210) is one of:

- `fulfilled` — `{ bindingName, inputJson, settledOrder, dateNowMs, valueJson }`
- `rejected` — `{ bindingName, inputJson, settledOrder, dateNowMs, error }`
- `interrupted` — `{ bindingName, inputJson, interruptionId, payloadJson }`

### 7.2 Dispatch on resume

`handleHostFunctionRequest` (manager.ts:757-830) indexes the ledger by request ordinal:
`fulfilled` → queue the **recorded** value, host function **not called**; `rejected` → queue the recorded
error, not called; `interrupted` without a resolution → park again; `interrupted` **with** a resolution →
**re-invoke** the host function with `context.resume` populated. Exactly one host function re-executes
per resume.

### 7.3 The correctness constraints

1. **Divergence hard-fails.** `assertReplayMatches` (manager.ts:959-976) compares `bindingName` **and**
   `inputJson` per ordinal and throws `RunProtocolError('Continuation replay diverged from the recorded
   host function ledger.')`. A replay that finishes early also fails: *"Continuation completed before
   replaying the full host function ledger."* (manager.ts:1098-1102).
2. **Guest nondeterminism is removed, not tolerated.** `Date.now()` is a counter seeded from
   `determinism.dateNowMs` and **incremented 1 ms per call**; `new Date()` with no args uses it;
   `Math.random()` is xorshift128+ from a recorded 128-bit seed (guest-sources.ts:168-252). Each ledger
   entry records the wall-clock `dateNowMs` at settle time and resets the guest clock to it. Guest time
   is therefore deterministic **and wrong**.
3. **Host functions must be idempotent where they can re-run.** Docs: *"Determinism … does not make host
   functions or external systems deterministic. Host functions remain responsible for protecting side
   effects with idempotency keys, request identifiers, or transactional application logic."*
4. **Non-replayed side effects do not repeat** — which is the point, but also means a host function whose
   *effect* the guest depends on re-observing (a cache warm, a lock) is wrong on replay.
5. **Cancellation does not unwind.** *"Cancellation stops the current invocation. It does not reverse a
   host side effect."* (cancellation.mdx:20-23).
6. **Large results are the practical ceiling.** The ledger stores every result verbatim;
   `maxContinuationBytes` defaults 32 MiB, `maxHostFunctionOutputBytes` 4 MiB. Eight max-size results
   and the continuation is unencodable. For a data agent pulling rows this is a real limit.
7. **Unawaited host calls are a hard error.** `__runAssertNoDetachedBridgeCalls` (guest-sources.ts:254-345)
   throws `RunDetachedBridgeRequestError` if the program returns with an unobserved or still-pending
   bridge request — which is what keeps the ledger a total order.

### 7.4 The token

`createSignedContinuationCodec` (continuation-codec.ts:192-283): envelope
`{ format: 'run-continuation', version: 1, algorithm: 'HS256', state, issuedAtMs, expiresAtMs, nonce }`;
body = canonical JSON (sorted keys; rejects cycles, sparse arrays, non-plain objects, non-JSON values) →
base64url; signature = `HMAC-SHA256('run.continuation.v1\0' || body, secret)` → base64url; token =
`body.signature`. Secret from `continuationSecret` or `RUN_CONTINUATION_SECRET`, **min 32 bytes**;
`verificationSecrets[]` for rotation. Verify uses `timingSafeEqual` **and** re-canonicalises the decoded
body and byte-compares it against what arrived — closing a class of parser-differential attacks.
Defaults: `maxAgeMs` 1 h, `maxTokenBytes` 32 MiB, `clockSkewMs` 60 s. With no secret configured, encode
and decode are replaced by a thrower (run.ts:15-21) — it fails closed rather than emitting unsigned
tokens.

Scope: `createContinuationScopeHash` (manager.ts:1160-1196) =
`sha256({ audience, bindingManifest, continuationContext, transformedSourceHash })`.

## 8. `just-bash` lineage — unverified, and contradicted in its strong form

**Claim under test (blog):** the Run SDK's runtime was extracted out of `just-bash`, where it was called
`js-exec`. **unverified (blog only).**

- The `run` repository contains **no occurrence** of `just-bash` or `js-exec` — not in source, docs,
  README, THIRD_PARTY_NOTICES, or the 50-commit history (`grep -rn` over the tree; `git log --all -S"just-bash"`
  returns nothing). No attribution to just-bash anywhere.
- The initial commit is a squashed import of an already-complete implementation — *consistent* with an
  extraction from somewhere, naming nothing.
- `just-bash@3.1.0` still ships `js-exec` in full, with its own direct `quickjs-emscripten@^0.32.0`
  dependency and no dependency on `run` (§1.2).
- Structurally they are different things. just-bash's `js-exec` is a **bash command** that deliberately
  provides the Node shims `run` deliberately refuses: `fs`, `child_process`, `process`, `Buffer`,
  `fetch`, `require()`/`import` of ~15 Node modules (just-bash README §"Node.js Compatibility", from the
  published 3.1.0 tarball). `run`'s guest has none of those.

**Most that can be said from primary sources:** two Vercel Labs projects independently embed
`quickjs-emscripten@0.32.0`. There *is* a closer conceptual cousin — just-bash's `javascript.invokeTool`
hook plus the `just-bash-executor` / `executor-js` approval-and-elicitation pipeline
([vercel-labs/just-bash](https://github.com/vercel-labs/just-bash), surfaced via web search) is the same
"guest calls host tools, host can require approval" idea `run` formalises as host functions +
interruptions. That is a resemblance, not a provenance.

### 9.2 The boundary

QuickJS-in-WASM (`newQuickJSAsyncWASMModule(RELEASE_ASYNC)`, worker.ts:401-411) inside a Node worker
thread (`node:worker_threads`, worker.ts:3). Fresh context per invocation; workers pooled but contexts
never reused. Verbatim scope statement:

> *"The sandbox is a separate JavaScript engine on a worker thread, with hardened globals, explicit host
> functions, serialization, and resource limits. **It is not a container, a virtual machine, or a
> separate operating-system process.**"* — [sandbox.mdx](https://github.com/vercel-labs/run/blob/main/content/docs/foundations/sandbox.mdx)

Verified in the guest prelude (guest-sources.ts:45-165): `crypto`, `performance`, `SharedArrayBuffer`
deleted then pinned `undefined`; `eval` → `undefined`; `Function` replaced by a thrower **and**
`constructor` overwritten on `Function`/`AsyncFunction`/`GeneratorFunction`/`AsyncGeneratorFunction`
prototypes (closing `(async()=>{}).constructor(...)`); ~40 intrinsics frozen and re-pinned
non-writable/non-configurable. No `fetch`, no timers, no `process`/`require`/`module`/`Buffer`, no
filesystem, no `import()`. Only host I/O is `console` (worker.ts:494-522) plus polyfilled `atob`/`btoa`.
Source runs as an **async function body** — top-level `await`/`return` work; TypeScript is
**type-stripped, not type-checked**.

Host-function names are validated before installation: identifier pattern, byte caps (512 namespace /
1024 qualified), rejection of `__proto__`/`constructor`/`prototype`/**`then`**, `__run` prefix, an
80-entry reserved-globals list, and an enumerability requirement (run.ts:26-165).

**What it does not protect against**, per its own docs:

> *"The sandbox controls what guest code can access directly, but host functions remain trusted
> application code. A broad host function grants broad authority, however well the sandbox itself is
> configured. … The sandbox is one part of the security model."* — sandbox.mdx, "Trust"

And the AI SDK's phrasing: *"Treat the sandbox as defense in depth. Generated code and tool arguments are
untrusted."* / *"every capability exposed by a provided tool is available to the generated program."*
([ai-sdk.dev/docs/ai-sdk-core/code-mode](https://ai-sdk.dev/docs/ai-sdk-core/code-mode)).

**Serialization:** devalue with custom `Error`/null-prototype reducers (`utils/serde.ts`), whose own
comment reads *"This is a durable replay wire format, not just an implementation detail."* Survives:
primitives, `undefined`, `BigInt`, `NaN`, `±Infinity`, `-0`, `Date`, `RegExp`, `Map`, `Set`,
`ArrayBuffer`, `DataView`, typed arrays, `Error`, `AggregateError`, cycles, sparse arrays. Does not:
functions, symbols, promises (awaited, not transferred), weak collections, class instances. Copies, not
references.

### 9.3 Bun

Bun support landed in `2.0.1` (commit `b5fff36`, 2026-08-24 — one day before this note). The worker
factory switches to `new Worker(INLINE_RUN_WORKER_SOURCE, { eval: true })` on Bun, and termination is
raced against a 100 ms grace timer with this comment:

> *"Bun's `worker_threads.terminate()` can hang (oven-sh/bun#12616 and follow-ups), including when the
> thread is busy in QuickJS WASM. Bound the wait so caller settlement and pool accounting can proceed."*
> — manager.ts:1253-1275

`destroyWorker` then swallows terminate failures (manager.ts:1283-1289). **On Bun, a `RUN_TIMEOUT` can
report a stopped run whose thread is still executing.** Atlas is bun-only (`bun >=1.4.0 <1.5.0`).

### 9.4 API surface and limits

Exports: `run`, `createRunner`, `getHostFunctionContext`, `isRunInterruptedResult`, `setMaxWorkers`,
`createSignedContinuationCodec`, `createStoredContinuationCodec`, and nine `RunError` subclasses
(index.ts).

Result union is **exactly two members** — `{ status: 'completed', value }` and
`{ status: 'interrupted', interruptions, continuation }` (types.ts:106-135). There is no `'failed'`
variant: every failure rejects. Discriminate with `RunError.isInstance(error)` + `error.code`; stable
codes are `RUN_TIMEOUT`, `RUN_SOURCE_TOO_LARGE`, `RUN_BRIDGE_LIMIT`, `RUN_HOST_FUNCTION_ERROR`,
`RUN_SERIALIZATION_ERROR`, `RUN_PROTOCOL_ERROR` (limits.mdx). QuickJS memory/stack exhaustion have **no**
dedicated codes.

Defaults (types.ts:49-73, cross-checked against limits.mdx — they agree): `timeoutMs` 30 s ·
`memoryLimitBytes` 64 MiB · `maxStackSizeBytes` 2 MiB · `maxSourceBytes` 256 KiB · `maxResultBytes` 1 MiB ·
`maxConsoleOutputBytes` 64 KiB · `maxHostFunctionArgumentsBytes` 1 MiB · `maxHostFunctionOutputBytes`
4 MiB · `maxBridgeRequests` 256 · `maxInFlightBridgeRequests` 32 · `maxContinuationBytes` 32 MiB.
Worker cap: memory-derived, ceiling 32, floor 1 (`runtime/max-workers.ts:3`, 48 MiB assumed overhead per
worker).

Docs guidance worth carrying into any adoption: *"Do not automatically retry a limit violation with a
larger budget. First determine whether the source is behaving as expected and whether host side effects
are safe to repeat."* (limits.mdx).

### 9.5 Relationship to code mode and Vercel Sandbox

[vercel/ai#18832](https://github.com/vercel/ai/pull/18832) — *"feat(code-mode): use run package for
code-mode execution"* — merged **2026-08-13**, +978/−4428 across 36 files. Body: *"the inner workings of
the code mode tool can now be abstracted by the `run` package … mapping added to convert AI SDK tools to
`hostFunctions`"*, with future work *"attach tool approvals to the `run` mechanism"*.
`@ai-sdk/code-mode@1.0.22` (2026-08-13) is the first version depending on `run: ^2.0.0`. Code mode does
**not** currently integrate with AI SDK tool-approval flows (ai-sdk.dev code-mode docs).

Vercel Sandbox is the sibling, per `run`'s README: *"`run` is for sandboxed JavaScript computation inside
an application. Workloads that need an operating system, package installation, or process-level isolation
should use Vercel Sandbox."* Atlas already uses Vercel Sandbox for both explore and Python
(`lib/tools/explore-sandbox.ts`, `lib/tools/python-sandbox.ts`), so the two would coexist at different
altitudes rather than compete.
