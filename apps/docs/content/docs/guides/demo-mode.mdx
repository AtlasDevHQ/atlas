<Callout type="warn" title="Self-Hosted Only">
  Demo mode is for operators running their own Atlas instance. On [app.useatlas.dev](https://app.useatlas.dev), contact the Atlas team to discuss demo and trial options for your organization.

Demo mode lets you expose a public, email-gated preview of Atlas at `/demo`. Visitors enter their email to start a sandboxed chat session — no account creation required. It's designed for lead capture and product evaluation with built-in rate limiting and reduced agent capabilities.

It also enables a second, narrower door: the [anonymous MCP demo](#anonymous-mcp-demo), which lets an MCP client (Claude Desktop, Cursor, Claude Code) query the demo workspace with **no account and no email** — the email is an optional act *after* the first answer. The email-gated web demo is unchanged by it.

<Callout title="Prerequisites">
- `ATLAS_DEMO_ENABLED=true`
- `BETTER_AUTH_SECRET` set (used to sign demo tokens)
- A datasource configured (`ATLAS_DATASOURCE_URL`)
</Callout>

---

## How It Works

1. Visitor navigates to `/demo` and enters their email address
2. Atlas validates the email and issues an HMAC-SHA256 signed token (24-hour TTL)
3. The visitor chats with the agent using the demo token for authentication
4. Sessions are rate-limited and capped at fewer agent steps than production

Demo sessions use a separate auth path from the main application. The demo token is derived from `BETTER_AUTH_SECRET` with a `:demo` suffix — it does not grant access to any authenticated endpoints.

### Lead Capture

Every demo start captures:
- Email address (used as the demo user identifier)
- IP address and user agent
- Session count and whether the user is returning

User IDs are deterministic hashes (`demo:<sha256(email)[0:16]>`) — the raw email is stored only in the lead capture record, not in conversation metadata.

## Configuration

### Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `ATLAS_DEMO_ENABLED` | `false` | Enable demo mode and the `/demo` route |
| `ATLAS_DEMO_MAX_STEPS` | `10` | Maximum agent steps per demo chat (1–100) |
| `ATLAS_DEMO_RATE_LIMIT_RPM` | `10` | Requests per minute per demo user (0 = disabled) |

```bash
# .env — enable demo mode with custom limits
ATLAS_DEMO_ENABLED=true
ATLAS_DEMO_MAX_STEPS=15
ATLAS_DEMO_RATE_LIMIT_RPM=20
```

## Demo vs Production

| Feature | Demo | Production |
|---------|------|------------|
| **Auth** | Email-gated token (24h TTL) | Managed auth, API key, or BYOT |
| **Agent steps** | Reduced (default 10) | Full (default 25) |
| **Tools** | Default tools only | All tools + plugin tools + actions |
| **Rate limit** | Separate per-user limiter | Main rate limiter |
| **Conversations** | Persisted with `surface="demo"` | Persisted with standard surface |
| **Token expiry** | 24 hours | Session-based |

<Callout type="warn">
Demo mode uses the default datasource and semantic layer. Ensure the demo datasource does not contain sensitive production data.
</Callout>

## API Endpoints

Demo endpoints are mounted at `/api/v1/demo`.

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `POST` | `/start` | None (rate-limited by IP) | Email gate — validates email, signs token, captures lead |
| `POST` | `/chat` | Bearer demo token | Stream a chat response (mirrors main chat) |
| `GET` | `/conversations` | Bearer demo token | List the demo user's conversations |
| `GET` | `/conversations/:id` | Bearer demo token | Get a conversation with messages |

### Start a Demo Session

```bash
curl -X POST https://your-atlas.example.com/api/v1/demo/start \
  -H "Content-Type: application/json" \
  -d '{ "email": "visitor@example.com" }'
```

Response:

```json
{
  "token": "eyJlbWFpbCI6InZpc2l0b3JAZ...",
  "expiresAt": 1742565600000,
  "returning": false,
  "conversationCount": 0
}
```

### Chat via Demo Token

```bash
curl -X POST https://your-atlas.example.com/api/v1/demo/chat \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJlbWFpbCI6InZpc2l0b3JAZ..." \
  -d '{ "messages": [{ "role": "user", "content": "Show me revenue by month" }] }'
```

## Anonymous MCP demo

The web demo asks for an email before the first answer. An MCP client has no form to put one in, so the hosted MCP endpoint exposes a second door, `/mcp/demo`, that answers first: it mints an **anonymous demo principal** — an identity that is not an email — scoped to the demo workspace only.

```bash
bunx @useatlas/mcp init --hosted --demo --write
```

That one command mints a session against the hosted demo (`https://mcp.useatlas.dev` by default; `--api-url` overrides) and writes an `atlas-demo` server entry into your MCP client's config, pointed at `/mcp/demo` with a short-lived bearer. Restart the client and ask it a question about NovaMart. Re-run the command when the token expires.

### What the anonymous principal can do

- Call `searchAtlas` against the demo workspace's Company Atlas — the facts granted to the whole workspace. Facts scoped to a private channel or audience are not visible.
- Call `executeSQL` against the demo workspace's datasource, through the same SELECT-only validation pipeline every other caller gets.
- Optionally call `shareEmail` **after** it has received at least one answer, to leave an email for updates. Before the first answer the call is refused; it is never required to keep querying.

### What it cannot do

- Reach any workspace other than the demo one. The workspace is resolved server-side from the `ATLAS_DEMO_WORKSPACE_SLUG` setting on every request, never from the request itself. A token minted for a different workspace, a session whose stored workspace disagrees, or an unresolvable slug all **fail closed** with a request id.
- Use `explore`, the semantic-layer tools, the NL `query` tool, prompts, resources, datasource-lifecycle tools, plugin tools, or anything that writes. The principal is a `member` carrying `mcp:read` only, and it runs the full MCP dispatch gate (billing → action policy → scope → RBAC → approval) like any hosted actor.
- Outlive its token. The default lifetime is two hours (`ATLAS_DEMO_ANON_TOKEN_TTL_MINUTES`), against the web demo's 24.
- Exceed either of two budgets: requests per minute per client IP (session mints and tool calls share it) and tool calls per minute per minted identity. Both are settings-registry entries.

Anonymous means **less reach than the email demo, never more** — in tool surface, role and token lifetime. The email demo runs the agent loop with its full default tool set (`executeSQL`, `explore`, the semantic-layer tools); the anonymous door registers exactly the three tools above. The one axis on which the anonymous door reaches something the web demo does not is `searchAtlas`: the web demo's principal is bound to no workspace, so the Company Atlas is unavailable to it, while the anonymous principal is bound to the demo workspace and sees its workspace-wide facts. That is the point of this door, and it is still a strictly narrower door than a real workspace member's.

### Settings

All four are platform-scoped, hot-reloadable, and hidden from workspace admins on SaaS. `ATLAS_DEMO_ENABLED=true` and `BETTER_AUTH_SECRET` are still the prerequisites, and the door needs an internal database (`DATABASE_URL`): it is where the demo workspace is looked up and where sessions are counted.

| Setting | Default | Description |
|---------|---------|-------------|
| `ATLAS_DEMO_WORKSPACE_SLUG` | `novamart-demo` | Slug of the one organization the anonymous principal may reach |
| `ATLAS_DEMO_ANON_IP_RATE_LIMIT_RPM` | `20` | Anonymous-demo requests per minute per client IP — mints and tool calls share the bucket (0 = disabled) |
| `ATLAS_DEMO_ANON_RATE_LIMIT_RPM` | `10` | Tool calls per minute per minted identity (0 = disabled) |
| `ATLAS_DEMO_ANON_TOKEN_TTL_MINUTES` | `120` | Token lifetime, 1–1440 minutes |

### Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `POST` | `/api/v1/demo/anonymous` | None (rate-limited by IP) | Mint an anonymous demo principal. Optional body `{ "client": "<label>" }`. Returns `token`, `expiresAt`, `sessionId`, `workspaceId`, `mcpUrl` |
| `POST` | `/api/v1/demo/anonymous/email` | Bearer anonymous demo token | Optionally attach an email — `409 answer_required` before the first answer |
| `POST` / `GET` / `DELETE` | `/mcp/demo` | Bearer anonymous demo token | The Streamable HTTP MCP endpoint (the `/mcp/demo/sse` alias also resolves) |

```bash
curl -X POST https://your-atlas.example.com/api/v1/demo/anonymous \
  -H "Content-Type: application/json" \
  -d '{ "client": "curl" }'
```

### What is stored

Every mint inserts one row in `demo_anonymous_sessions` — `id` (the identity), `created_at`, `expires_at`, `workspace_id`, a hashed IP (`ip_hash`, an HMAC under a key derived from `BETTER_AUTH_SECRET`; **no raw IP at rest**), the client label, `answer_count`, and `email_captured_at`. An email shared through `shareEmail` or the REST endpoint goes to `demo_leads` through the same lead-capture path the web demo uses; the session row keeps only the timestamp. To count anonymous sessions in a window:

```sql
SELECT count(*) FROM demo_anonymous_sessions WHERE created_at >= '2026-10-01';
```

## Operator: demo funnel analytics

The endpoints above are the visitor path. Operators watch the funnel — who started a demo, what they asked, and what it cost — from a separate **platform-admin** surface mounted at `/api/v1/platform/demo`. Every route requires the `platform_admin` role **and** MFA, and needs an internal database (`DATABASE_URL`). Lead emails and the questions visitors ask are PII-adjacent, so platform-admin gating *is* the access control for this data.

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/config` | Current demo model, max-steps, and RPM, plus the resolved effective model |
| `PUT` | `/config` | Update the demo model, max-steps, and RPM |
| `GET` | `/leads` | Demo leads with per-email session + conversation counts and a token/cost spend rollup |
| `GET` | `/transcript?email=<addr>` | The full question/answer transcript for one lead email |
| `GET` | `/metrics` | Token + cache + latency rollup — aggregate and per-model |

### Changing demo limits without a redeploy

`PUT /config` writes `ATLAS_DEMO_MODEL`, `ATLAS_DEMO_MAX_STEPS`, and `ATLAS_DEMO_RATE_LIMIT_RPM` to the settings registry at platform scope. They are **hot-reloadable** — a change takes effect within the settings refresh window (~30s), no restart required. The [environment variables](#environment-variables) above are the boot default; once the internal DB is up, the operator console (or `PUT /config`) is the authoritative surface for these three knobs. A blank `model` clears the override and reverts the demo to the resolved default model.

## Limitations

These apply to the email-gated web demo. The [anonymous MCP demo](#anonymous-mcp-demo) is narrower still — see its own list.

- **No plugin tools** — demo sessions use default tools only (executeSQL, explore). Custom actions and plugin-provided tools are not available
- **No write operations** — actions are disabled in demo mode
- **Reduced steps** — the agent has fewer steps to work with, which may limit complex multi-step analyses
- **Token expiry** — demo tokens expire after 24 hours; the user must re-enter their email to continue
- **Rate limiting** — each demo user is rate-limited independently from production users
